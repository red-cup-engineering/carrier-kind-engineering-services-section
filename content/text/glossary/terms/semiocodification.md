# Semiocodification — candidate name for making semiotic operations executable

**Semiocodification** is the Leader's candidate word. Its most useful *non-duplicative* definition is **the realization of a qualified semiotic relation or composition as executable, typed semiotic code**. It should name the *code-production passage*—principally a SignChain program/rule/derivation and, where required, SignCraft realization—not indiscriminately describe graphing, addressing or making an information cell. The term is **provisional** until a distinct actual source-owned producer and consumer demonstrate the need for its name. Do not form a semiocodification engine or a parallel toolchain merely to instantiate it.

**Admitted input:** Original source-bearing cells, a lawfully defined composition or operation, input/output types, relevant truth/knowledge witness semantics, guards, rights and source derivation obligations. **Output:** A typed program or executable operation *expressed through the existing computer-code / SignChain / SignCraft producer*, keeping the original source and admitted refusal paths. **Invalid output:** A JSON list of steps claimed to be executable without a consumer, a directed graph declared to be code, or the assertion that similarity to Obsmetrologia proves an interpreter correct.

The distinction is testable. Cellularizing a request yields a cell. Chaining two type-compatible claims yields a candidate or proved composition depending on rule evidence. Graphing them establishes explicitly represented incidences. **Semiocodifying** occurs only when an actual native program/interpreter can take the admitted composition as input and perform its specified computational step. Executing an effectful program remains a separate Systems/authority boundary; a type-checked term cannot invoke an unauthorized server.

Prefer **semiotic chaining** for ordered relations and **semiotic graphing** for networks unless this executable-code distinction is materially useful. This avoids having three evocative nouns for the same transformation, prevents the current leaf-library proliferation problem and preserves the hard algebra → logic → language → geometry → dynamics derivation direction rather than imposing the final software graph as an Obsmetrologia axiom.
